# STEP 1. 現在サイトの構造分析

## 1-0. 本調査の制約（先に明示）

本設計を行った実行環境はネットワークポリシーにより `sisicreation.com` および
`studio.design` / `help.studio.design` への直接アクセスがブロックされていた。
そのため**サイト本体のDOM・全ページ一覧・STUDIOプロジェクト設定は未検証**である。

本章は以下で構成する。

1. 外部（検索インデックス・報道・プレスリリース）から**検証できた事実**
2. そこから導かれる**構造上の論点**
3. 実装前に**必ず確認すべきチェックリスト**（所要15分・STUDIO編集画面で完結）

3のチェックリストの結果次第で変わる設計判断には、本書全体で `【要確認】` を付けている。

### 構造的に重要な発見

**① SISIDENの一次情報が、自社ドメインの外に分散している。**

確認できた作品の解説・背景情報は、以下に散在している。

- 代表 note（`note.com/sisitsukahara`）
- クライアント企業の note・広報ページ（進和建設工業、コクー等）
- PR TIMES
- 地域メディア（はなれじま広報部 等）
- 東京新聞 広告局メディア

つまり現状、**「SISIDENが取材した一次情報」の受け皿が sisicreation.com に存在しない**。
記事化の価値はここにある。分散している文脈をSISIDEN自身のドメインに集約し直すことが、
本プロジェクトの第一の意味である（被リンク・引用・AI参照の集約点をつくる）。

**② 検索インデックスに、STUDIOの自動生成パスが露出している。**

検索結果に以下が出現する。

```
https://sisicreation.com/qZyarGFP/8PXjMlic     （タイトル: 株式会社シシクリエイション - Sisi）
```

これはSTUDIOがページ作成時に自動採番するランダムパスで、**パス未設定のまま公開**された
ページがインデックスされている状態を示す。

- SEO上: 意味を持たないURLがインデックスされ、クロールバジェットと評価が分散する
- AIO上: AIが出典URLを提示する際に意味不明な文字列が出る
- 運用上: STUDIOの**ページパスは公開後に変更するとリダイレクトなしで404化**する（後述）

→ **SISIDEN MEDIA構築前に、既存ページのパス棚卸しを行うこと。**
これは本プロジェクトのStep 0（実装前作業）とする。

**③ ブランド表記が `SisiDen` / `SISIDEN` で揺れている。**

プレスリリースは `SisiDen`、今回の設計要件は `SISIDEN`。
固有名詞の表記揺れはAI検索のエンティティ解決（同一実体と認識させること）で不利に働く。

→ **正式表記を1つに固定**し、全面統一する。本設計書では `SISIDEN`（全大文字）を正、
日本語併記を「シシデン」とする。旧表記 `SisiDen` は Organization の
`alternateName` に入れてAIに同一性を伝える（STEP 8参照）。

STUDIOのCMSダッシュボードで確認した内容。

### 既存モデル

|---|---|---|

| 投稿者 | 1 | 通常モデル |
| 制作事例 | 5 | 通常モデル |
| メンバー | 1 | 通常モデル |

```
アクティブモデル数   5 / 10
公開アイテム数      31 / 5,000
```

### ここから読み取れること

**① 残枠は5。本設計の8モデルはそのままでは入らない。**
[STEP 5-8の縮退案](./05-studio-cms-model.md)の適用が確定した（下の 1-2 論点C に確定版の割り当てを記載）。

**② タグ型・カテゴリー型はモデル枠を消費していない可能性が高い。**
一覧には9モデルが並んでいるのに「アクティブモデル数」は5。
枠を消費していない4つは、いずれもタグ型・カテゴリー型のアイコンを持つモデルと一致する。

→ **【要確認・1分】** 新規モデル作成時にモデルの種別を選べるか。
選べる場合、`CATEGORIES` `TAGS` `AREAS` `ORGANIZATIONS` をカテゴリー型/タグ型で作れば
**枠を消費せずに済む可能性がある**。これが成立すると縮退の必要自体がなくなる。

**③ 記事モデルが2つに分裂している（新着記事21件 / 記事3件）。**
既存サイトの構造なので今回は触らないが、SISIDEN MEDIAで同じことを起こさないこと。
記事は `ARTICLES` 1モデルに統一し、区別は `CATEGORIES` への参照で行う。

また、同一内容のアイテムが「公開中」と「下書き」で二重に存在しているものがある
（マンション管理の記事が `UDNbxh6J`（公開中）と `gOQ4npEM`（下書き）の2件）。
修正時に複製して作業した名残と思われる。

→ SISIDEN MEDIAでは**アイテムを複製して修正しない**。
既存アイテムを直接編集し、`status` で公開/下書きを切り替える。
複製が必要な場合は、作業後に必ず不要な方を削除する。

**④ CMSアイテムのSlugが全件ランダム文字列になっている。**

```
/ 3JcLQK8w    / 5g0juwaJ    / obSu3uk0    / 3qf6AZnX    / DKq2MgxC
```

[1-1](#1-1-外部から検証できた事実)で検索インデックスに現れていた
`sisicreation.com/qZyarGFP/8PXjMlic` の正体はこれ。
**既存記事のURLはすべて意味を持たない文字列**になっている。

| 影響 | 内容 |
|---|---|
| SEO | URLにキーワードが含まれず、被リンクのアンカーにもならない |
| AIO | AIが出典URLを提示したときにブランドも内容も読み取れない |
| 共有 | SNSでURLを見ても何の記事か分からない |

→ **SISIDEN MEDIAでは、アイテム作成時にSlugを必ず手入力する**ことを運用ルールにする
（[STEP 4-4 スラッグ命名規則](./04-url-design.md)）。
既存記事のSlug変更は404を招くため、別途移行計画として扱う（1-4 Step 0）。

**⑤ 既存記事の中にSISIDENのコンテンツ資産がある。**
「鉄を継ぐもの」「物語の力は、人口500人の村を救えるか？」「八丈島の台風復興ドキュメンタリー」
「AI時代、エンジニアはどう生きるのか」など、作品の告知記事が既に存在する。

→ これらは**そのまま `DOCUMENTARIES` の初期データになる**。
告知記事（お知らせ）と作品ページ（ドキュメンタリー）は別物として作り直す。

## 1-2. 現状の構造上の論点

### 論点A. SISIDENが「制作実績」として扱われている構造

コーポレートサイトの情報設計では、SISIDENは通常「事業内容」または「実績」の
1ブロックとして配置される。この構造のままメディアを足すと、読者にはこう見える。

> 映像制作会社が、自社の制作実績を解説している

これは要件22の「最重要条件」と正面から衝突する。SISIDENは**第三者視点の編集メディア**
として立たなければならない。よって、

- SISIDEN MEDIAは**独自のグローバルナビゲーションを持つ**（コーポレートのナビを継承しない）
- SISIDEN配下では**コーポレートのロゴをヘッダーに出さない**
- 接続点は**フッターの `Produced by SISI CREATION` のみ**
- 記事内で自社を主語にしない（「弊社が制作した」ではなく「SISIDENが取材した」）

### 論点B. YouTubeが唯一の入口になっている

現状、作品への入口はYouTubeのみ。YouTubeは以下の弱点がある。

- 検索エンジンからの流入は動画枠に限定される
- テキストがないためAI検索が内容を引用しにくい（字幕は引用元として弱い）
- 視聴後の回遊先がYouTubeの推薦アルゴリズムに支配される
- 取材した情報量の大半が使われない（10分に収まらない）

→ Webメディア化の本質は「記事を増やすこと」ではなく、
**YouTubeに預けている資産の管制塔を自社ドメインに建てること**。

### 論点C. モデル枠が5しか残っていない（確定）

同一プロジェクトに構築するため、上限はコーポレートサイトと**合算**される。

| リソース | 上限 | 使用済み | 残り |
|---|---|---|---|
| CMSモデル数 | 10 | **5** | **5** |
| CMSアイテム数 | 5,000 | 31 | 4,969 |
| 公開ページ数 | 300 | 要確認 | - |

アイテム数とページ数は問題にならない。**制約はモデル枠5つのみ。**

#### 確定版の枠の割り当て

本設計の8モデルを、残5枠に収める。

| モデル | 扱い | 消費枠 | 着手 |
|---|---|---|---|
| `DOCUMENTARIES` | 通常モデル | 1 | Phase 1 |
| `ARTICLES` | 通常モデル | 1 | Phase 1 |
| `PEOPLE` | 通常モデル | 1 | Phase 1 |
| `ISSUES` | 通常モデル | 1 | Phase 2 |
| `AREAS` | 通常モデル | 1 | Phase 3 |
| `CATEGORIES` | **カテゴリー型**（不可ならセレクトプロパティ） | 0 | Phase 1 |
| `TAGS` | **タグ型**（不可ならマルチセレクト） | 0 | Phase 2 |
| `ORGANIZATIONS` | **カテゴリー型**（不可ならテキスト） | 0 | Phase 3 |
| | | **合計 5 / 5** | |

ぴったり収まる。ただし**予備枠がゼロ**になるため、以下を守る。

- モデルを思いつきで追加しない
- 新しい分類軸が欲しくなったら、まず既存モデルのセレクト/マルチセレクトで表現できないか考える
- どうしても6枠目が必要になったら、Business Plusへの変更、または
  既存の「新着記事 / 記事」2モデルの統合（コーポレート側の整理）を検討する

**Phase 1で使うのは3枠だけ**（DOCUMENTARIES / ARTICLES / PEOPLE）。
2枠を残したまま始められるので、当面の圧迫はない。

### 残る最大の分岐（プランはBusinessで確定済み）

Businessプランのため**どちらも選べる**。分岐点は「誰が記事を書き、どこで更新するか」。

```
記事を書いて更新するのは誰か？
├─ 編集部がSTUDIOの編集画面で書く
│    → STUDIO CMS ネイティブ構成（STEP 5 方式A）
│    → 8モデル×約30プロパティを最初に手作業で作る必要がある
```

ただし初期は片方に寄せるほうが破綻しない。

## 1-4. Step 0（設計確定前に着手してよい作業）

1. 既存ページのパス棚卸しと整理（`qZyarGFP` 等の自動生成パスの是正 / 不要ページの非公開化）
2. ブランド表記を `SISIDEN` に統一（YouTube チャンネル名・各種プロフィール含む）
3. Google Search Console / Google Analytics の登録状況確認
4. YouTube 公開済み全作品の棚卸し（タイトル・公開日・URL・登場人物・地域・企業）
   → そのまま STEP 5 の DOCUMENTARIES モデルの初期データになる
5. 取材済みで未公開の一次情報の棚卸し（インタビュー録・撮影素材・取材ノート）
   → これが記事の在庫。**記事企画は「書けるもの」からではなく「既に取材したもの」から立てる**
